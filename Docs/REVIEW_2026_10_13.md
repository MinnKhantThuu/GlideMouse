# App Review investigation: 0.4.2 (26)

Apple rejected the submitted mouse-control use of Accessibility/PostEvent and
Input Monitoring/ListenEvent, and reported that Next remained disabled after
granting access on macOS 27.2. These are separate issues. Changing UI labels or
fixing onboarding does not itself satisfy the permission-policy objection.

## Onboarding correction in build 28

- Next no longer requires both permission preflight results to be true.
- Button identification inside GlideMouse uses events delivered to its own
  AppKit view and can run without global input access.
- Completing setup with missing/partial access saves settings and keeps the
  global engine paused. It does not grant, fake or bypass system permission.
- Returning from System Settings refreshes permission state immediately.
  Periodic checks also run in common run-loop modes.
- Store permission wording distinguishes mouse event posting from the AX
  accessibility service and mentions the system pane's different macOS names.

Validation on macOS 26.6.2: 94 core tests; 46 UX checks including eight setup
checks for denied, partial and granted permissions; native Next navigation
through all three steps; app-local right-click identification with no global
access; universal arm64/x86_64 archive; compiled English/Myanmar/Chinese strings.
The preview uses isolated fixtures, no input runtime and temporary settings.
Native automation failed when reading the final settings window because its
helper crashed; completion/paused-state checks were verified in the UX harness.

This is not a clean-install physical mouse test on macOS 27.2. The review device's
permission-result discrepancy has not been reproduced on that OS. Do not claim
that every runtime/permission problem is resolved based on these checks.

## Policy and binary checks

The local version-26 archive and matching local package binaries import Core
Graphics PostEvent/ListenEvent APIs, not AXIsProcessTrusted or AXUIElement calls.
The new build-28 exported payload is Apple Distribution signed and contains
`com.apple.security.app-sandbox = true`. No private touch adapter, updater,
privilege escalation, or enabled preview mode is included.

An export from an unsigned archive was observed to drop Sandbox entitlements.
The package validator rejects that artifact. The corrected release is exported
from a signed archive and checked after packaging, rather than inferring
entitlements from Xcode settings or from a separate development build.

[Apple DTS](https://developer.apple.com/forums/thread/820594) distinguishes
PostEvent/ListenEvent from the Accessibility TCC service and describes their
Sandbox compatibility. DTS expressly cannot determine App Review policy.
[Guideline 2.4.5](https://developer.apple.com/app-store/review/guidelines/#2.4.5)
and the review team's specific response still govern the submission.

An honest reply should ask Apple to reassess or clarify the public Core Graphics
API use. GlideMouse is a general mouse utility; do not describe it as a disability
aid solely to overcome the rejection. Removing system-wide input processing
would remove the core features and requires a separate product decision.

Submission and policy resolution remain separate from build/test completion.
