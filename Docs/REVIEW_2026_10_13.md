# App Review investigation: 0.4.2 (26)

Apple rejected the submitted mouse-control use of Accessibility/PostEvent and
Input Monitoring/ListenEvent, and reported that Next remained disabled after
granting access on macOS 27.2. These are separate issues. Changing UI labels or
fixing onboarding does not itself satisfy the permission-policy objection.

## Onboarding correction in build 28

- Next no longer requires both permission preflight results to be true.
- Button identification inside GlideMouse uses events delivered to its own
  AppKit view and can run without global input access.
- Completing setup with missing/partial access saves settings and keeps the
  global engine paused. It does not grant, fake or bypass system permission.
- Returning from System Settings refreshes permission state immediately.
  Periodic checks also run in common run-loop modes.
- Store permission wording distinguishes mouse event posting from the AX
  accessibility service and mentions the system pane's different macOS names.

Validation on macOS 26.6.2: 94 core tests; 46 UX checks including eight setup
checks for denied, partial and granted permissions; native Next navigation
through all three steps; app-local right-click identification with no global
access; universal arm64/x86_64 archive; compiled English/Myanmar/Chinese strings.
The preview uses isolated fixtures, no input runtime and temporary settings.
Native automation failed when reading the final settings window because its
helper crashed; completion/paused-state checks were verified in the UX harness.

This is not a clean-install physical mouse test on macOS 27.2. The review device's
permission-result discrepancy has not been reproduced on that OS. Do not claim
that every runtime/permission problem is resolved based on these checks.

## Policy and binary checks

The local version-26 archive and matching local package binaries import Core
Graphics PostEvent/ListenEvent APIs, not AXIsProcessTrusted or AXUIElement calls.
The new build-28 exported payload is Apple Distribution signed and contains
`com.apple.security.app-sandbox = true`. No private touch adapter, updater,
privilege escalation, or enabled preview mode is included.

An export from an unsigned archive was observed to drop Sandbox entitlements.
The package validator rejects that artifact. The corrected release is exported
from a signed archive and checked after packaging, rather than inferring
entitlements from Xcode settings or from a separate development build.

[Apple DTS](https://developer.apple.com/forums/thread/820594) distinguishes
PostEvent/ListenEvent from the Accessibility TCC service and describes their
Sandbox compatibility. DTS expressly cannot determine App Review policy.
[Guideline 2.4.5](https://developer.apple.com/app-store/review/guidelines/#2.4.5)
and the review team's specific response still govern the submission.

An honest reply should ask Apple to reassess or clarify the public Core Graphics
API use. GlideMouse is a general mouse utility; do not describe it as a disability
aid solely to overcome the rejection. Removing system-wide input processing
would remove the core features and requires a separate product decision.

Submission and policy resolution remain separate from build/test completion.

## Input Monitoring removal in build 30

- The event tap now contains only mouse buttons, wheel, motion and drag events. Keyboard key-down, key-up and flags-changed events are excluded.
- Emergency pause is registered with Carbon `RegisterEventHotKey`; a conflict is reported with menu-bar pause as the available fallback. The integration harness exercises the real Carbon handler inside its own process rather than posting a system-wide shortcut.
- Device discovery reads IORegistry metadata and HID element descriptions, without opening HID input devices. Stable registry IDs prevent connection polling from repeatedly rebuilding the input runtime. Reconnection detection can take up to two seconds; action dispatch does not use that polling timer.
- Setup and runtime readiness require only mouse-control/event-posting access. The UI no longer requests or links to Input Monitoring.
- Store package validation rejects ListenEvent request/preflight and HID input-opening imports in addition to the existing AX/private API checks.

Validation: 94 core tests, 48 Store UX checks, 15 primary-button integration checks, mouse remapping/scroll phases/capture isolation/native passthrough and registered hotkey integration. All 679 translations passed checks against the compiled Store bundle. The actual Apple Distribution-signed universal package contains App Sandbox and no Input Monitoring request/preflight or HID input-opening APIs. No existing user settings or installed direct edition were replaced.

A separate sandboxed test identity was granted only mouse-control access by the user and never requested Input Monitoring. On macOS 26.6.2, the read-only ListenEvent preflight returned true after posting access was allowed. That effective preflight result must not be described as an independently denied ListenEvent privilege. Access to the TCC database was unavailable; no permissions were reset or widened to read it. Input Monitoring request removal is established by source, UI and signed-binary checks, plus runtime execution with only the user-requested posting grant. macOS 27.2 validation and App Review acceptance remain unproven.

Build 29 was uploaded first. The physical test harness was corrected to recognize its own process identity when launched from the command line, and the final replacement is build 30. The validation window is scoped to the test app so background mouse use retains normal actions. Synthetic window calibration passed. Mac Mouse Fix was discovered enabled during the initial physical attempts and was temporarily disabled for an isolated retest. The physical attempts captured ordinary clicks but no side-button or wheel sequence; physical remapping therefore remains unverified. Mac Mouse Fix was restored to its original enabled state after testing.

## Build 30 rejection and build 31 correction, 24 October 2026

App Store Connect confirms that Apple rejected 0.4.2 (30) on 20 October under Guidelines 2.4.5 and 2.4.5(v). The attached screenshots show a real Keystroke Receiving consent dialog and the Input Monitoring settings entry. The earlier Next-button completeness objection was not repeated. This does not establish that every setup issue has passed review.

The previous artifact check was too narrow. `InputRuntime.setCaptureArea` and `beginLearning` could create a global listen-only tap, including before PostEvent access. Device discovery also constructed IOHIDDevice objects before filtering their usages. Build 31 removes listen-only taps, requires PostEvent before every runtime tap, and lets the capture view handle its own AppKit events. Device discovery now reads registry dictionaries and published element descriptors without an HID user client. The source generator rejects listen-only taps and HID-client creation. Package validation now rejects HID-client imports and uses `explicitListenEventAPIsAbsent` rather than implying that a symbol scan proves runtime consent behavior.

A development-signed, sandboxed identity `app.glidemouse.privacycheck31` was launched through Launch Services with no permission grants. Ten denied-state checks passed. Both PostEvent and ListenEvent preflights were false before and after local left/right/middle event capture, learning, attempted enabling, configuration saving and emergency pause. No global tap was created. The runtime, model, device registry, hotkey handler and capture view were byte-identical to the release source. The ordinary setup UI also proceeded from step one to step two without either grant or an Input Monitoring dialog. The mouse was absent during the final check, so device-specific physical behavior is not certified.

A shell launch initially inherited the host's effective input permissions. That run was rejected by the test's fresh-identity guard and is not denied-state evidence. The passing check used a normal application launch. No existing app permissions were reset and no extra access was granted to read the test app's protected container.

Validation on macOS 27.0.1: 94 core tests, 49 Store UX checks, 679 compiled translations in English/Myanmar/Simplified Chinese, and synthetic integration checks for remapping, scroll phases/momentum, capture isolation, native passthrough and the registered pause handler. The integration run had posting access available; it is separate from the fully denied test and does not certify a physical mouse or macOS 27.2.

The reply sent to Apple at 16:39 Asia/Bangkok on 24 October explains these corrections and the remaining public PostEvent use. It describes concrete ways user-selected mouse actions can reduce key combinations and repeated wheel input, without claiming clinical testing or disability certification. It asks for reassessment or a technical review if that use remains disallowed. At the time of that reply, Store signing was still being completed.
